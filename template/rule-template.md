## 任务目录骨架

```text
<workDir>/
├── task-list.jsonl
└── <任务名>/
    ├── meta/
    │   ├── rule.md
    │   ├── cache/
    │   ├── script/
    │   └── runs/
    └── <报告>.md
```

| 路径 | 作用 | 何时出现 |
|---|---|---|
| `task-list.jsonl` | 任务元数据唯一权威；本文件不重复名称、执行时间、时区、开关、保留天数 | 创建任务时 |
| `meta/rule.md` | 任务规则 + 缓存清单 + 脚本清单 | 创建任务时 |
| `meta/cache/` | 稳定数据 | 创建任务时 |
| `meta/script/` | 脚本，优先 Python | 创建任务时 |
| `meta/runs/` | 每次运行一个 JSON，由插件写入 | 首次运行 |
| `<报告>.md` | 历次报告，全部留在任务根目录 | 首次运行 |

`meta/` 是任务资料区：`rule.md`、`cache/`、`script/` 由任务执行维护，`runs/` 由插件写运行记录。不要手工改坏，也没有提交/还原动作。

## 执行要求

### 1. 目标最小化

1. 默认只做「完成用户目标所需的最小集合」：不自行增加数据源、分析维度、图表、建议或额外交付物。
2. 只有「任务细节」里明确写出的额外目标才做；追加目标不能顺手改变原有口径、范围或输出格式。
3. 报告结构（结论 → 关键事实 → 数据来源 → 建议动作）是输出格式，不算新增目标；没有建议就写「无」或不写，不能为了填满而编造。

### 2. 数据与缓存

1. 行情、汇率、新闻、排名、库存、状态等每次可能变化的数据，不放入 `meta/cache/`，也不登记为可复用缓存；每轮重新获取。脚本需要时用本次运行的临时数据，运行结束不保留。
2. 已确认或大概率不会变化的数据（标的清单、代码映射、历史分红、口径定义、接口字段说明、模板）放入 `meta/cache/`。以「功能 / 领域」为单位一个文件，例如 `bank-list.json`、`dividend-history.csv`，不要把所有数据塞进一个文件。
3. 缓存用 JSON / CSV 等机器可读格式；字段、单位、口径、as-of（数据截止日期）、来源固定；不存网页正文或散文。脚本应能直接读取，不用模型再解析。
4. 新增、更新或删除稳定数据时，同步更新本文件的「缓存清单」：文件名、存储内容（含口径和 as-of）、可用场景。拿不准是否稳定时，按实时数据处理，不缓存。

### 3. 执行前的数据规划

每次执行开始，先列出本轮需要的数据项，再动手取数：

1. 已缓存且仍有效 → 直接读；
2. 已缓存但可能过期 → 做轻量校验（as-of / 版本 / 关键字段），必要时刷新；
3. 未缓存、接口稳定 → 用固定脚本获取；
4. 未缓存、需要联网确认 → 先确认来源、时间和口径，再取；
5. 无法获取 → 标记缺失，按规则回退或停下；不编造、不猜。

凡是接口稳定、参数可枚举的数据获取、校验、转换，都写成 `meta/script/` 下的脚本；重试、字段映射、单位换算、去重和基本校验固定在脚本里，不要每轮让模型重新拼请求或解析页面。模型只做需求理解、数据分类、异常判断和必要的定性分析，不做逐条数据搬运、格式转换和报告排版。

### 4. 报告生成

1. 数据准备完成后，报告由 `meta/script/` 下的固定生成脚本产出；同一任务使用同一个生成脚本，报告模板、字段、排序都在脚本里。
2. 脚本输入是结构化数据（`meta/cache/` 的稳定数据 + 本轮获取的数据；本轮数据通过临时文件或标准输入交给脚本，不落缓存），输出写到执行指令给出的报告路径。
3. 缺失字段必须显式输出「缺失 / 待确认」，不能静默省略、补零或编造。脚本失败时先修数据或脚本，不要改用手写报告绕过。
4. 需要改报告结构或口径时，改 `meta/script/` 里的脚本并更新「脚本清单」；不要每轮临时写新脚本。模型只负责运行脚本、核对输出、说明异常，不改写脚本生成的正文。

## 输出约定

- 报告结构：结论 → 关键事实 → 数据来源 → 建议动作。
- 报告中引用 `meta/cache/` 里的数据时，写明文件名。
- 缺失数据显式标注「缺失 / 待确认」，不补零、不编造。
- 本次执行新增或更新了数据/脚本，必须同步更新本文件的「缓存清单」/「脚本清单」。
